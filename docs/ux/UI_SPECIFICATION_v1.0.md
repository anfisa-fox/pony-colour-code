# Pony Colour Code — UI Specification

**Status:** Draft  
**Version:** 0.1  
**Date:** 10 августа 2026

---

## 1. Purpose

Документ фиксирует **композицию и UX** MVP Pony Colour Code: три основных экрана (START → GAME → RESULT), игровой цикл, модель feedback и требования к будущим визуальным assets.

Документ **не определяет** финальную палитру, типографику, персонажные изображения и CSS-реализацию. Эти решения — этап Visual Design.

**Источники:** MVP Contract v0.2, Architecture v0.1, First Playable (Core Gameplay verified PASS).

**Правила MVP (неизменны):** 4 позиции · 6 Mane 6 · 10 попыток · повторы разрешены · интерфейс на русском.

---

## 2. UX Principles

Pony Colour Code — **самостоятельная игра**, воспринимаемая пользователем как **отдельная игровая комната внутри My World**.

- Игра **не копирует** визуальный стиль My World; допустим более яркий, игровой, тематический MLP-стиль.
- **Простая композиция:** минимум экранов, понятный цикл, отсутствие лишней навигации.
- **Приоритет игрового поля** над декоративными элементами.
- **Responsive layout** от ~375 px; одна layout-модель для всех устройств.
- **Дружелюбный тон:** победа мотивирует сыграть ещё; поражение не воспринимается как наказание.

---

## 3. Navigation Flow

```
START
  ↓ «Играть»
GAME
  ↓ победа / поражение
RESULT
  ↓ «Новая партия» / «Попробовать ещё раз»
GAME (новая независимая партия)
```

Дополнительно на START и RESULT (и ненавязчиво на GAME):

`← Вернуться в My World`

Отдельный router не используется; переключение экранов — state machine приложения (см. Architecture v0.1).

---

## 4. START Screen

**Назначение:** за несколько секунд объяснить игру и позволить начать партию.

### Верхняя зона

Ненавязчивый элемент навигации:

`← Вернуться в My World`

### Центральная зона

- **Название:** `Pony Colour Code`
- **Подзаголовок (по смыслу):** «Угадай секретный набор пони — как Mastermind, только с магией дружбы.»
- Допустим **небольшой декоративный тематический элемент** около названия. Конкретный visual asset **не фиксируется** на этом этапе.

### Правила

Три коротких шага:

1. Выбери 4 пони из палитры. Повторы разрешены.
2. После попытки игра подскажет, насколько ты близко к секрету.
3. У тебя 10 попыток, чтобы разгадать код.

### Feedback legend (стартовая)

Кратко показать три типа подсказок. На wireframe использовались временные обозначения:

| Wireframe placeholder | Значение | Финальный token |
|----------------------|----------|-----------------|
| 😀 | Пони и место угаданы | MLP Smile (Exact) |
| 😉 | Пони есть в секрете, но в другом месте | MLP Wink (Partial) |
| 😶 | Пони отсутствует в секрете | MLP Oops (Miss) |

**Важно:** обычные emoji — только **временные placeholder**. Финальный MVP использует **собственные тематические feedback tokens** в стилистике MLP (см. раздел 13).

### Primary Action

Крупная основная кнопка:

`Играть`

### Дополнительная информация

Допустимо:

`Одна партия · примерно 5–10 минут`

### Сознательно отсутствует на START

- выбор режима;
- настройки сложности;
- статистика, профиль;
- tutorial wizard;
- G5 и дополнительные меню.

## 5. GAME Screen

**Главный экран приложения.**

Приоритет интерфейса (сверху вниз по важности):

1. **История попыток**
2. **Текущая догадка**
3. **Палитра персонажей**

### Header

Компактный; не занимает значительную часть экрана.

Содержит:

- название `Pony Colour Code`;
- количество оставшихся попыток, например: `Осталось попыток: 7 / 10`;
- ненавязчивый возврат в My World.

### Secret (до завершения партии)

Секрет **не показывается**. Допустимо компактное обозначение:

`?  ?  ?  ?`

Отдельный крупный блок secret **не создаётся**.

### Actions

| Действие | Поведение |
|----------|-----------|
| `← Удалить` | Удаляет последний выбранный элемент текущей догадки |
| `Подтвердить` | Отправляет комбинацию из 4 персонажей |

`Подтвердить` **disabled**, пока выбрано менее четырёх персонажей. Primary action визуально **отличается** от secondary.

---

## 6. Guess History

Каждая завершённая попытка — **отдельная компактная строка**.

Структура строки:

```
[номер]  [4 персонажа]     [feedback group]
```

Пример:

`1   [Tw] [RD] [AJ] [PP]     [feedback]`

Требования:

- номер попытки;
- 4 выбранных персонажа;
- **отдельная группа feedback tokens** (не под каждым персонажем);
- строки достаточно компактны, чтобы история не вытесняла текущую игру.

## 7. Feedback System

### 7.1 Основной визуальный язык

Текстовые подписи вида `Точно: N` / `Не на месте: N` **не являются** основным визуальным языком финального интерфейса.

Основной feedback — **четыре эмоциональных token'а на попытку**, отражающих агрегированный результат Mastermind.

### 7.2 Три состояния token'ов

| Token | Состояние | Wireframe | Финал |
|-------|-----------|-----------|-------|
| **Smile** | Exact — персонаж угадан **и** на правильном месте | 😀 | Дружелюбная улыбающаяся MLP-style эмоция |
| **Wink** | Partial — персонаж **есть** в secret, но **в другой позиции** | 😉 | MLP-style подмигивающая эмоция |
| **Oops** | Miss — совпадения нет | 😶 | MLP-style «упс» / лёгкое дружелюбное удивление |

**Запрещено:** негативная, расстроенная или «наказывающая» эмоция для Miss.

### 7.3 Критическое правило: tokens ≠ позиции

Feedback tokens относятся ко **всей попытке**, а не к конкретным слотам догадки.

Пример:

```
Guess:    [A] [B] [C] [D]
Feedback: 😀  😉  😶  😶
```

**НЕ означает:** A→😀, B→😉, C→😶, D→😶.

Это означает только: **1 exact, 1 partial, 2 miss**.

Следствия для UI:

- feedback tokens собраны в **отдельную компактную группу**;
- между четырьмя guess slots и feedback group — **достаточное визуальное разделение**;
- **нельзя** располагать feedback token непосредственно под каждым персонажем.

### 7.4 Ordering

Детерминированное представление для визуальной стабильности:

**Exact → Partial → Miss**

Пример: 2 exact + 1 partial + 1 miss → `😀 😀 😉 😶`

Порядок **не несёт позиционной информации** — только читаемость.

### 7.5 Feedback legend на GAME

Компактная легенда на игровом экране:

- **MLP Smile** → пони + место
- **MLP Wink** → пони есть, место другое
- **MLP Oops** → пони нет

Достаточно понятна при первом запуске, но **не занимает значительную часть** игрового поля.

### 7.6 Accessibility

Визуальная группа token'ов должна иметь **доступное текстовое описание**.

Пример:

- Визуально: `[Smile] [Smile] [Wink] [Oops]`
- Для assistive tech: «2 точных совпадения, 1 частичное совпадение, 1 отсутствует»

---

## 8. Current Guess

Текущая попытка — **отдельная хорошо заметная** строка/область.

Содержит **4 слота:**

`[ 1 ] [ 2 ] [ 3 ] [ 4 ]`

После выбора персонажа соответствующий slot заполняется.

Индикатор прогресса:

`Выбрано N из 4`

(или эквивалентный компактный индикатор).

---

## 9. Character Palette

Палитра содержит **только Mane 6:**

- Twilight Sparkle
- Rainbow Dash
- Applejack
- Pinkie Pie
- Fluttershy
- Rarity

Каждый персонаж в финальном UI распознаётся **не только по цвету**. Минимум:

- визуальный образ / портрет / символ персонажа;
- имя или доступная текстовая идентификация.

**Повторный выбор** одного персонажа **разрешён**.

После заполнения четырёх слотов дальнейший выбор **блокируется** до удаления или submit.

## 10. RESULT Screen

**Один экран** для двух состояний: **WON** и **LOST**. Два архитектурно независимых экрана **не создаются**.

### 10.1 WON

Показать:

- позитивное поздравление;
- раскрытый secret;
- количество **использованных** попыток;
- крупную кнопку `Новая партия`;
- возврат в My World.

Главная эмоция экрана: **«Хочу сыграть ещё одну партию»**.

Не превращать в reward system. Коллекционные награды — Post-MVP.

### 10.2 LOST

Показать:

- дружелюбное сообщение, например: `Почти получилось!`;
- раскрытый secret;
- факт использования 10 попыток;
- основную кнопку `Попробовать ещё раз`;
- возврат в My World.

Поражение **не должно** восприниматься как наказание.

### 10.3 Visual placeholder

На RESULT допускается место для **небольшой тематической MLP-style эмоциональной иллюстрации**.

В MVP:

- без сложной анимации;
- без reward system;
- без unlock mechanics.

Конкретный asset **не фиксируется** на этом этапе.

---

## 11. Responsive Behaviour

Одна responsive layout-модель.

| Контекст | Поведение |
|----------|-----------|
| **Mobile (~375 px+)** | Приоритет: текущая попытка → персонажи → feedback → действия |
| **Desktop** | Может использовать дополнительное горизонтальное пространство |

Отдельное мобильное приложение или отдельная мобильная архитектура **не создаются**.

---

## 12. Accessibility

Сохраняются требования MVP Contract и Architecture:

- интерактивные элементы — **реальные `<button>`** (и ссылки для навигации);
- **видимый keyboard focus**;
- **понятный disabled state**;
- персонажи **не различаются исключительно цветом** — символ/имя/`aria-label`;
- feedback имеет **доступное текстовое описание** (см. §7.6).

## 13. Visual Assets to Be Designed

### 13.1 MLP-style Feedback Tokens (отдельные assets)

Три состояния в **единой стилистике:**

1. **Smile** — Exact
2. **Wink** — Partial
3. **Oops** — Miss

Требования:

- визуально ассоциируются с MLP;
- дружелюбные, хорошо различимы в малом размере;
- работают как игровые символы;
- не требуют чтения текста после знакомства с легендой.

**Не должны:**

- выглядеть как системные emoji;
- быть фотографическими;
- быть чрезмерно детализированными;
- использовать разные визуальные стили между собой;
- сообщать позицию конкретного персонажа.

Визуальное решение token'ов потребует **отдельного согласования** на этапе Visual Design.

### 13.2 Прочие assets (намеренно неопределены)

- финальная цветовая палитра и фоны;
- типографика;
- персонажные портреты / изображения (`public/characters/`);
- декоративный элемент START;
- RESULT illustration;
- animation details.

---

## 14. Explicit Non-Goals

UI MVP **не проектирует:**

- mode selector, School of Friendship, Canterlot, Duel;
- G5 и расширенные палитры;
- настройки N / M / K;
- statistics, achievements, collection, unlock system;
- editor;
- audio controls;
- сложные animations;
- PWA UI;
- authentication / profile.

---

## 15. Wireframe Status

Композиционно рассмотрены три wireframe:

| Wireframe | Определяет | Не определяет |
|-----------|------------|---------------|
| **START** | иерархию, правила, legend, primary action | палитру, шрифты, финальные assets |
| **GAME** | history, current guess, palette, feedback model, actions | размеры, персонажные изображения, финальные tokens |
| **RESULT** | win/loss messaging, secret reveal, new game | reward UI, анимации, иллюстрации |

Wireframes зафиксированы как **композиционная основа** для Visual Design; First Playable реализует **функциональный каркас** без финального визуала.
